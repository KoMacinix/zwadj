# D356 — règle des rouges, des portes, de l'e2e et des campagnes, commitée AVANT toute passe et avant le premier code

**Sources** : la consigne du rang 58 (`docs/preuves/D356/consigne.md`), R-1 à R-8 et § 3 ; la table d'ouverture ; `docs/preuves/D355/regle-portes.md` (dont les cas 1 à 3 de « ce qu'on fait d'un rouge », par `docs/preuves/D352/regle-portes.md`) ; R-9 de D340 (batterie) ; R-15 de D343 (deux passes e2e) ; D334, item 5 (les rouges avant le code) ; D304, D305, D312, D316, D323, D352 (une morsure se LIT).

⛔ **Ce que ce document est** : des critères et des prédictions écrits AVANT de mesurer. Il ne dit pas ce que les mesures donneront ; une mesure qui contredit une prédiction se lit et s'écrit comme telle (D291), elle n'est pas « corrigée » ici après coup.

## 1. Les rouges — contre l'état d'avant, versés AVANT le premier commit de code

**Ce que « rouge » veut dire, par famille** (écrit avant de les jouer ; aucun de ces tests n'est joué à l'écriture de ce document) :

- **MP-12 — le secret HMAC absent** (`apps/api/src/config/env.spec.ts`) : production sans la variable ⇒ une exception qui NOMME la variable ; développement sans elle ⇒ idem ; trop courte (< 32) ⇒ idem. **Prédiction : ROUGE sur une `AssertionError`** (« expected [Function] to throw an error » : `validateEnv` ne la connaît pas). C'est un rouge de DÉFAUT d'absence mesurable par assertion.
- **MP-10, le générateur et la liste fermée des PIN triviaux** (`staff-pin.spec.ts`), **le hacheur** (`staff-pin-hasher.spec.ts`) : les modules **n'existent pas** : leurs specs tombent à la **COLLECTE** (import d'un module absent), comptés à part (« fichiers tombés à la collecte »), jamais comme des tests en échec.
- **R-4, l'état du PIN** (`staff-account-state.spec.ts`, la fonction jumelle) : l'export n'existe pas ⇒ **`TypeError`** (« … is not a function »), compté comme tel — **jamais une morsure**.
- **Le contrat** (`staff-contract.spec.ts` : le schéma de K-23, la parité FR = AR des clés de message de validation) et **le client d'API** (`staff-client.test.ts`) : le schéma et la méthode n'existent pas ⇒ `TypeError` ou collecte ; la parité des catalogues ne rougit qu'une fois les clés écrites d'un côté.
- **MP-1, MP-2, MP-3, MP-15, MP-26, MP-27, MP-28 par la route K-23** (`staff-pin.int-spec.ts`) : la route n'existe pas ⇒ **404 là où 200 ou 401 est attendu** : **`AssertionError`** (« expected 404 to be 200 » ; les statuts se lisent par `expect(res.status).toBe(…)` de vitest, jamais par `.expect(<statut>)` de supertest, D305). **Prédiction : rouge par assertion**, pour la raison que la route manque : ce sont des rouges d'ABSENCE, pas la preuve qu'une garde mord.
- **L'émission et l'effacement** (`staff-pin-issue.int-spec.ts`) : K-14, K-15 et K-18 rendent un PIN UNE fois (`Cache-Control: no-store`) ; K-21 et K-22 effacent le PIN. **Prédiction : rouge par assertion** (`body.pin` est `undefined` aujourd'hui ; les colonnes `pin_*` restent posées après la réinitialisation). **Ce sont les rouges de DÉFAUT du lot** : l'état d'avant ne fait pas ce que la consigne demande, et le test le dit par une assertion sur le comportement RÉEL de routes qui existent.
- **R-3, les quatre courses** (`staff-pin-race.int-spec.ts`) : PIN ‖ PIN par la route (20 requêtes parallèles) — rouge par assertion (404) ; PIN ‖ réinitialisation, PIN ‖ désactivation, PIN ‖ déblocage par mot de passe — **par l'entrelacement forcé sur les méthodes du magasin** (la réservation, l'ouverture par PIN), qui **n'existent pas** : ces trois sont des rouges d'**ABSENCE par `TypeError`** (« store.reservePinAttempt is not a function »), comptés comme tels. ⚠ **Aucune de ces courses n'est un rouge de défaut** : le défaut qu'elles gardent n'existe pas dans le code d'avant, parce que le code d'avant n'a pas de PIN. **Leur morsure est celle de la neutralisation (§ 4).**
- **R-5, le journal du PIN** (`staff-pin-audit.int-spec.ts`) : les lignes `staff.pin_login`, `staff.pin_login_failed`, `staff.pin_lock`, `staff.pin_unlock` ne s'écrivent pas aujourd'hui ⇒ « expected 0 to be 1 » : rouge par assertion ; **le test du journal RÉEL** (aucun PIN, aucun haché dans une ligne ni dans le journal des requêtes) ne peut pas rougir avant que le PIN existe : il n'est pas un rouge, il est une garde posée, mordue par la neutralisation.
- **R-6, `quote.promote`** (`quote-promote-actor.int-spec.ts`) : la ligne porte `actor_member_id` quand une session de personnel existe, et reste nulle quand la couche est éteinte. **Prédiction : rouge par assertion** pour le premier cas (« expected null to be '…' »), **VERT dès aujourd'hui** pour le second (couche éteinte : nulle partout) — **ce n'est pas un rouge, et le dire est le point** : une garde posée sur un comportement déjà tenu, mordue par la neutralisation.
- **Le contrôle des débits** (`throttle.int-spec.ts`, la clé `staffPin`) : 429 après la limite ; aujourd'hui 404 ⇒ rouge par assertion. **La liste fermée des routes exemptées** (`staff-source-guards.spec.ts`, `staff-session-guard.int-spec.ts`) : cinq au lieu de quatre ⇒ rouge par assertion tant que le contrôleur n'a pas sa cinquième.
- ⚠ **Prédiction d'ensemble, écrite pour pouvoir être contredite** : à l'exception de MP-12, de l'émission, de l'effacement, du journal et de R-6 (rouges par assertion sur un comportement), **la majorité des rouges de ce lot sont des rouges d'ABSENCE** (collecte, `TypeError`, 404) : ils prouvent que les tests ne passent pas à vide, **pas** qu'une garde mord — la morsure vient de la neutralisation de `neutralize-r58.py`.
- **Pièces** : la commande, l'empreinte sha256 de CHAQUE fichier de test joué (l'octet de l'arbre de travail au moment du jeu), la sortie lue contre l'état d'avant, la classification de chaque échec (`AssertionError` · `TypeError` · collecte · autre). Elles entrent dans un commit **ANTÉRIEUR au premier commit de code** (D334, point 5).

**Après le code**, un test modifié n'est jamais affaibli : toute correction d'un test après son rouge est **déclarée** (empreinte avant / après), comme au § 5 de D341 et à D355.

## 2. Préparation, état machine, ce qu'on fait d'un rouge des portes

1. `git status --short` vide ; `git fetch` puis local = `origin/main` + les commits du lot en début de chaque passe ; ports 3100, 3101, 5273 et 5274 libres ; Docker lancé, `zwadj-db` « Up » ; `headless_shell` à 0.
2. **Sur batterie : aucune porte, aucune campagne, aucune mesure de durée** (R-9 de D340, D290) — la session s'arrête et le dit.
3. Aucun fichier n'est édité pendant qu'une porte, une campagne ou une mesure le lit (D270).
4. Les cas 1 à 3 de `docs/preuves/D352/regle-portes.md`, § 4, **s'appliquent tels quels** : un rouge dans un fichier du lot est un défaut du lot (corriger, rejouer les portes EN ENTIER, dire la première passe) ; un rouge hors du lot ⇒ **un seul rejeu** de la porte entière, `retries` inchangé (0), aucun délai changé ; un rejeu rouge ⇒ rien n'est poussé.
5. **L'intermittence d'amorçage des tests d'intégration** (« Nest can't resolve dependencies of the JwtAuthGuard … Reflector », D355, consigne 1 e) **dort** : si elle revient, la session **ne relance pas à l'aveugle** ; elle verse la trace COMPLÈTE de la première occurrence (`docs/preuves/D356/intermittence/`), essaie la piste (externaliser `@nestjs/*` dans `vitest.config.int.ts`) sur une COPIE hors du dépôt, et rapporte ; **rien n'est commité dans la configuration**.

## 3. Les six portes — UNE passe, par le pilote de D340, non modifié

`bash docs/preuves/D340/portes/passe-secteur.sh <dossier hors dépôt>` : `typecheck`, `lint`, `test`, `build`, `test:int`, `test:e2e`, en série, **après la DERNIÈRE modification de code** ; aucun rejeu automatique. Les journaux bruts portent des jetons de développement et des **PIN de test** : versés **MASQUÉS** par `masquer-jetons.py` (la copie de `docs/preuves/D354/neutralisation/masquer-jetons.py`, une PIÈCE, rejouée telle quelle sauf si la mesure dit qu'elle ne masque pas un PIN de quatre chiffres — alors la forme des PIN de test s'écrit dans le test pour qu'elle se masque, jamais l'outil retouché sans l'écrire), le compte des suites restantes rapporté. **Prédiction** : les six à 0 ; le lot n'écrit ni écran ni migration ni montant ; `test:e2e` **ne mesure pas ce lot** (aucune spec ne joue le PIN) : elle **garde** que le serveur d'API de l'e2e démarre AVEC la variable du secret posée par `playwright.config.ts` (sans elle il refuserait de démarrer : c'est la seule chose neuve que cette porte voit), et que la connexion du personnel se comporte comme avant. Le dernier relevé : 109 passés + 1 ignoré, 110 listés ; l'attendu est **dérivé** par `playwright test --list` avant la passe.

## 4. Les campagnes

1. **Jamais en parallèle d'une porte** (une campagne MUTE des fichiers sources, D270). En série, sur secteur. L'ordre et l'identité de l'arbre sont celles de D355 (S-262) : les campagnes que le lot touche se jouent avant les portes ou après elles, **sur le MÊME arbre**, attesté par `git status --porcelain` vide ET `git diff --stat <SHA du commit de code> -- apps packages e2e` vide, à l'entrée et à la sortie de chaque campagne et de chaque porte ; le rapport imprime les deux relevés.
2. **`python3 neutralisation/neutralize-r58.py --int`** : **chaque garde neuve est neutralisée, son échec LU** à la première ligne du bloc d'échec (`AssertionError`, D304 ; un délai, un `TypeError` ou une collecte à zéro ne sont jamais une morsure ; une erreur de requête de Testing Library non plus, D352). L'empreinte sha256 du harnais est imprimée en tête de chaque journal ; **un harnais modifié en cours de campagne ⇒ la campagne est rejouée EN ENTIER**. **Une assertion native seulement** : `toBe`, `toEqual`, `toBeNull`… jamais `.expect(<statut>)` de supertest. Les cibles couvrent : l'état du PIN (chaque état de sa fonction), la liste des PIN triviaux, le générateur (borne, rejet), le hacheur (liaison au membre, comparaison à temps constant), la réservation atomique (le plafond, la condition du verrou, la condition de l'appareil), l'enregistrement de l'échec (le verrou posé AU troisième échec seulement, la fin des sessions), l'ouverture par PIN (chacune de ses quatre conditions sous verrou), l'émission (la règle une seule fois, le déblocage), l'effacement (K-21 et K-22), l'échéance de l'appareil, les quatre lignes du journal et leur charge fermée, le secret (le refus au démarrage, la longueur), la ligne de la promotion et la liste des routes exemptées.
3. **Les campagnes que le lot TOUCHE** : `lancer-touchees.py` (la copie de `docs/preuves/D354/neutralisation/lancer-touchees.py`, une PIÈCE rejouée telle quelle), qui croise `git diff` depuis le SHA de départ avec les fichiers que lit chaque campagne ; la liste attendue (table d'ouverture, § conditionnels) : `r44`, `r56`, `r57`, `r41`, `r43` — **hypothèse, à relever par l'outil**, pas une liste écrite d'avance. **Prédiction** : au moins une ancre de `neutralize-r44.py` et de `neutralize-r56.py` est périmée par ce lot (le magasin et le port du personnel changent de forme : les paramètres de `activate`, `openSession`, `changePassword`, la liste des méthodes) ; une ancre périmée est révisée par **extension de la table, AVANT le commit du harnais**, et la campagne est **rejouée EN ENTIER**.
4. Les empreintes sha256 de TOUS les harnais sont relevées avant et après : identiques sauf ceux que le lot modifie (déclarés) et `neutralize-r58.py` (neuf).
5. Une campagne n'est jamais déclarée verte sans que sa ligne de résumé ait été **lue** (« N garde(s) mordue(s) sur M cible(s) · 0 muette · 0 non mesurée ») ; « ERREUR DE SCRIPT » = campagne **arrêtée**.

## 5. L'e2e — deux passes complètes, vertes, consécutives (R-15 de D343)

Passe 1 : celle du pilote. Passe 2 : `pnpm test:e2e` seul, juste après. **Deux passes vertes consécutives ⇒ la porte e2e est verte.** Le lot ne touche aucun écran : l'e2e ne MESURE pas le PIN ; elle garde le démarrage du serveur d'API avec le secret jetable, et le parcours existant. Dit pour que « 109 passés » ne se lise pas comme une preuve du lot.

## 6. Ce que ce lot écrit sur la machine de Ko (déclaré ici, repris au rapport — règle de D337)

- **La base de développement de Ko : ni lue ni écrite.** `test:int` travaille sur `zwadj_test` et l'e2e sur `zwadj_e2e`, recréées à chaque lancement, sur le serveur de `zwadj-db`. **Aucune migration** n'est écrite ni appliquée.
- **Aucun `.env` n'est lu ni modifié** : la présence du NOM de la variable du secret dans `apps/api/.env` est COMPTÉE par un script qui n'imprime que ce nombre (forme de D330, R-2), au début et à la fin ; aucune valeur n'est lue à l'écran, versée ni imprimée. Rien dans `apps/pro` ni `apps/client` ; rien du chemin de l'argent ; aucun secret réel : la valeur du secret des tests est un jeton jetable écrit dans la configuration des tests, **audité avant chaque versement** (D298), et les PIN de test sont des valeurs de test.
- **Le geste de Ko** (ajouter la variable à son `apps/api/.env`) est écrit pas à pas dans `docs/preuves/D356/secret-pin-ko.md` ; sans lui l'API refuse de démarrer sur son poste. La session ne le fait pas.

## 7. Ce que ce lot n'écrit pas

Les écrans du personnel et de verrouillage (L36-4) ; le recours d'un Manager seul ; le changement de rôle et la réactivation ; la recherche d'annuaire (L36-5) ; un second mécanisme de limite de débit (D128 : le levier est unique) ; la correction de l'intermittence de l'amorçage ; une migration.
