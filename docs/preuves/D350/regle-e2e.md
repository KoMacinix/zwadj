# D350 — règle de la preuve e2e et des portes, commitée AVANT les passes (R-15 de D343)

1. **Les rouges avant le code** (D334, point 5) : `docs/preuves/D350/rouges/rouges.md` est commité AVANT tout commit de code d'application (`apps/`, `packages/`). Chaque pièce porte l'empreinte sha256 du fichier de test joué. Les tests s'écrivent contre le code d'AVANT (ils doivent rougir pour la raison que le lot corrige) ; une garde neuve qui ne rougit pas contre l'état d'avant, ou qui rougit pour une autre raison que celle qu'elle nomme, est lue et traitée avant de continuer. **Le premier rouge est celui de R-2** (la file des suppressions) : s'il est VERT, la garde reste, rien n'est changé, et la session le dit (R-2).
2. **Chaque garde neuve mord** : chaque cible de `neutralisation/neutralize-adm2.py` est neutralisée, le rouge est LU (une assertion `expect(...)`, jamais un délai ni un plantage — D304, D305, D312, D316), puis la mutation est restaurée. Zéro muette, zéro non mesurée. **Le journal de chaque passe commence par l'empreinte sha256 du harnais** ; **un harnais modifié en cours de campagne ⇒ la campagne est rejouée EN ENTIER**. La campagne de `neutralisation/neutralize-adm1.py`, que R-2 et R-3 touchent, est rejouée EN ENTIER (72 cibles à l'ouverture) ; une ancre qui ne trouve plus son texte est une cible à REPOSER, pas une cible muette.
3. **Les six portes** s'exécutent APRÈS la dernière modification de code, sur l'arbre propre, dans cet ordre : `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm test:int`, `pnpm test:e2e` ; la première passe est celle du pilote `docs/preuves/D340/portes/passe-secteur.sh` (non modifié). Chaque porte est rapportée avec son code de sortie et ses chiffres.
4. **L'e2e complète DEUX fois de suite, sur secteur** : la première dans le pilote, la seconde par `pnpm test:e2e` seul, juste après. **Attendu : 97 passés + 1 ignoré (le total de D349) + les tests de la spec neuve `e2e/specs/r52-administration.e2e.ts`**, dont le nombre est relevé par `playwright test --list` quand la spec est commitée et écrit dans le rapport des portes AVANT la première passe ; zéro échec, aucun rejeu. **Deux passes vertes ⇒ la porte e2e est verte ; un seul rouge ⇒ arrêt, pas de poussée** (R-15 de D343) : une passe rouge est LUE, jamais relancée pour verdir.
5. **Poste** : secteur (`BatteryStatus` = 2), RAM libre relevée, `chrome` et `headless_shell` à 0, Docker lancé, ports 3100, 3101, 5273 et 5274 libres, arbre propre. **Batterie : aucune porte, aucune passe** (R-9 de D340) ; la session s'arrête et le dit.
6. **Les journaux bruts des serveurs portent des jetons de développement** (courriels d'activation journalisés) : ils sont versés MASQUÉS par `masquer-jetons.py` (copie de D348, non modifiée), avec le compte des jetons restants assertés à zéro avant l'écriture ; ce qui ne peut pas être masqué n'est pas versé. Un audit de secrets (`neutralisation/audit-secrets.py`, sortie scellée par `--sortie`) précède CHAQUE versement ; toute alerte absente de la sortie scellée précédente se trie au contexte (D299).
7. **Aucune écriture sur la base de développement de Ko.** L'e2e travaille sur `zwadj_e2e`, l'intégration sur sa base de test (recréée par `setup-global`) ; le script du premier admin n'est JAMAIS joué sur la base de Ko (R-10) ; **la spec e2e élève un compte en ADMIN dans `zwadj_e2e` seulement**, comme r37 et r50. Toute écriture sur le serveur PostgreSQL de Docker est déclarée au rapport (commande, heure, effet).
8. **Un éditeur ne touche aucun fichier pendant qu'une vérification le lit** (D270) ; une campagne qui MUTE des fichiers sources ne tourne jamais en parallèle d'une porte.
9. **Les campagnes existantes concernées** (`neutralisation/lancer-campagnes.py`) sont jouées pour les fichiers que le lot touche ; ce script compare à `HEAD` : sur un arbre propre il ne voit rien (D348, S-171), donc la liste se relève AVANT le dernier commit de code ou se dérive des fichiers touchés depuis le SHA de départ `b8e5511`, et se joue par l'invocation explicite de chaque campagne concernée.
