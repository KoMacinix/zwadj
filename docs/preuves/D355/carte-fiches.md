# D355 — la CARTE de tous les chemins qui créent ou modifient une fiche client (R-2, versée AVANT tout code)

**Comment elle est relevée** (consigne, R-2 : « tu les relèves dans le code, jamais de mémoire ») : par RECHERCHE dans `apps/api/src` à l'état de départ `cc653dd`, hors specs et code généré — l'instrument est le contrôle **4.a** de `lecture-adverse/confronter-consigne.py` : **151 fichiers `.ts` parcourus, quatre motifs d'écriture cherchés** (`INSERT INTO`, `UPDATE`, `DELETE FROM pro_client_records` ; `proClientRecord.(create|createMany|update|updateMany|upsert|delete|deleteMany)`), **4 sites trouvés dans 2 fichiers** — puis par LECTURE de chaque site et de ses appelants. Le dossier de preuves, `apps/api/test/**` et `apps/api/prisma/migrations/**` sont écartés : les tests écrivent la table par SQL pour poser leurs fixtures (`UPDATE pro_client_records SET linked_user_id …`), les migrations la créent.

⚠ **Ce que la carte dit, et ne dit pas** : elle dit où le CODE DE PRODUCTION écrit la table aujourd'hui. Elle ne dit pas qu'aucun site n'en naîtra : **le lien d'une fiche à un compte** (`linked_user_id`, `linked_at`) n'est écrit nulle part dans le serveur aujourd'hui (seuls des tests le posent, par SQL) ; le lot qui le livrera (L35-5, numéro vérifié) sera un **cinquième site** — et la garde de SOURCE de ce lot (`client-record-writes.spec.ts`, § 4) le fait rougir tant qu'il n'est pas déclaré ici avec sa ligne de journal.

## 3. La forme de la ligne (proposition de la session — décisions S-258 et S-257, **à ratifier**)

```
actor_id        = userId du Bearer (le compte commun)          actor_role = "PRO"
actor_member_id = memberId de la session de personnel          | NULL (couche éteinte)
action          = client_record.create | client_record.update | client_record.complete_names
entity_type     = "client_record"                              entity_id  = l'identifiant de la fiche
after           = { "fields": ["phone", "email", "nameAr", "nameLatin"] (sous-ensemble, ordre fixe) }
                  + { "quoteId": "<uuid>" } pour K-5 SEULEMENT
before          = jamais écrit
```

**Pourquoi les NOMS des champs et jamais leurs valeurs** (MP-33 ; « pas de copie complète d'une fiche si les champs modifiés suffisent », R-2 ; même règle que D349 et S-81 de D339 : « aucun nom, aucun numéro, aucun e-mail » dans le journal) : le journal dit **qui** a touché **quelle** fiche, **quels** champs et **quand** ; il ne recopie pas le numéro, l'e-mail ni le nom d'une personne. Un journal qui garderait les valeurs serait une seconde copie des données personnelles, hors de leur correction. `fields` se dérive du **même objet** que celui que l'instruction écrit (les clés de `data`, les champs non nuls de l'insertion) : le journal ne peut pas dire autre chose que ce qui a été écrit. **`quoteId`** (K-5 seulement) est un identifiant, pas une donnée personnelle : il distingue « le nom a été complété par la boîte de langue du devis X » de « le pro l'a complété directement » sans multiplier les noms d'action.

## 4. Ce qui TIENT la carte (garde de SOURCE, neutralisée — `apps/api/src/clients/client-record-writes.spec.ts`)

Une garde lit les sources de `apps/api/src` (hors specs et code généré) et exige : (a) **l'ensemble des fichiers qui écrivent la table égale exactement** `pro-client-store.prisma.ts` et `quote-store.prisma.ts` ; (b) **le nombre de sites d'écriture par fichier** (3 et 1) égale le nombre d'appels au constructeur de la ligne de journal du MÊME fichier ; (c) aucune écriture de la table dans `quotes.service.ts` (la conversion). **Un cinquième site — un fichier neuf, ou une écriture ajoutée — fait rougir la garde tant que la carte et le journal ne le portent pas.** La garde se NEUTRALISE (cibles de `neutralize-r57.py`) : sans elle, « une carte » n'est qu'une photographie.

## 5. Ce que cette carte ne couvre PAS (écrit, pas tu)

Les écritures d'une fiche par un chemin **hors de l'API** (un accès direct à la base, un script) ; le **coût** d'une ligne de journal par écriture ; **qui lit** le journal (aucun écran, aucune route ne le lit : DR9 MS-3 en fera le « carnet horodaté des accès » à la mise en service) ; les **lectures** de fiche (K-1 rechercher n'écrit rien et n'est pas journalisé : DR5 liste la recherche d'annuaire, pas la recherche de fiche du pro).
