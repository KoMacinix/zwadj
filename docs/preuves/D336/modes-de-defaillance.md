# D336 — rang 41 — L35-4 amendé : les modes de défaillance, écrits AVANT le code

Consigne v3 du relecteur (adoptée par Ko le 22/10/2026), § 6 h : « Modes de défaillance, écrits AVANT le code ». Ils reprennent la liste de la consigne, mot pour mot dans leur intitulé, et les modes M-1, M-2, M-4, M-6, M-7, M-11 et M-24 du cadrage du rang 35 qui portent sur ce lot. Pour chacun : ce qui casserait, la garde (où elle vit : la base, un module pur, le service, l'écran) et ce qui la mesure. **Méthode NORMALE avec la garde d'égalité stricte de M-4.** Aucune ligne de code n'est écrite avant le commit de ce fichier.

| id | ce qui peut mal tourner | garde | mesure |
|---|---|---|---|
| **MD-1** | **Deux membres créent la même fiche en même temps** (deux postes du même pro, un double clic) : deux fiches pour une personne (M-1) | la base : `UNIQUE (pro_profile_id, phone) WHERE phone IS NOT NULL` et `UNIQUE (pro_profile_id, email) WHERE email IS NOT NULL` ; l'adaptateur : `INSERT … ON CONFLICT DO NOTHING`, puis relecture — jamais « lire puis insérer » | intégration sur PostgreSQL réel : dix créations simultanées du même numéro ⇒ UNE ligne, et les dix réponses portent le même identifiant |
| **MD-2** | **Le numéro et l'e-mail désignent deux fiches DIFFÉRENTES** (K-2 ; ou K-3b qui donnerait à une fiche le numéro d'une autre) : une fusion silencieuse, ou une 500 sur l'index unique | module pur (la décision de création) ; l'adaptateur traduit la violation d'unicité de K-3b ; **rien n'est fusionné** | intégration : `409 CLIENT_RECORD_IDENTIFIERS_CONFLICT`, et les deux fiches sont relues inchangées |
| **MD-3** | **E-mail de casse différente** (« Amina@Mail.DZ » et « amina@mail.dz »), espaces, forme Unicode : deux fiches pour une adresse | UNE fonction, `normalizeContactEmail` (`@zwadj/types` : rogné, NFKC, minuscules), appliquée par le contrat de K-1, K-2 et K-3b (S-55) | unitaire (la fonction, dont NFKC) ; intégration : la création par une casse est retrouvée par l'autre |
| **MD-4** | **Le numéro du pro, son second numéro, son e-mail** tapés comme contact du client (F-5, M-11, DB-8 étendue) | module pur (`estContactDuPro`, formes canoniques des deux côtés) ; refus à K-2 et K-3b (S-54) ; K-1 ne lit pas `users` (MD-10) | unitaire (les trois, plus un contrôle négatif) ; intégration : `400 CLIENT_IS_PRO_CONTACT` pour chacun des trois |
| **MD-5** | **Numéro fixe ou étranger** accepté ; **numéro écrit TOUT en chiffres arabo-indiens** accepté | le contrat partagé (`dzPhoneSchema`, `packages/types/src/phone.ts`) — mesuré par la troisième lecture : les trois rendent `null` | intégration : `400` à K-1 et à K-2 pour chacun ; **HORS LOT, connu** : un MÉLANGE de chiffres arabo-indiens et latins est accepté (« ٠555123456 » rend +213555123456) — non corrigé ici, ouvert au backlog |
| **MD-6** | **Fiche liée** modifiée par le pro (« champs grisés ») ; nom d'un devis changé sur une fiche liée (« le pro ne peut pas changer un nom prérempli, sauf si la fiche vient de son propre catalogue ») | module pur (`peutModifier`, la copie d'une fiche liée) ; l'adaptateur écrit sous `WHERE linked_user_id IS NULL` ; l'écran grise les noms | intégration sur une fiche liée posée en base par le test : K-3 et K-3b ⇒ `409 CLIENT_RECORD_LINKED` ; K-4 avec un nom différent ⇒ `409`, avec les noms de la fiche ⇒ créé ; l'écran : les champs de nom sont désactivés |
| **MD-7** | **La copie du nom écrasée** (M-6) : la boîte de langue remplace un nom présent ; deux boîtes simultanées ; la fiche modifiée après la remise réécrit le devis | K-5 : `UPDATE … WHERE client_name_x IS NULL`, compte = 1 exigé, sinon `409 QUOTE_CLIENT_NAME_ALREADY_SET` ; K-3 : même règle sur la fiche ; K-3b ne touche AUCUNE copie de devis (R8) | intégration : une copie présente n'est jamais remplacée ; deux compléments simultanés ⇒ un seul gagne ; modifier la fiche laisse la copie et le PDF inchangés |
| **MD-8** | **C-C3 violée** : la boîte complète la FICHE alors que le nom du devis diffère de celui de la fiche (M-24 : deux personnes, un numéro) | K-5, dans la même transaction : la fiche ne se complète que si le nom de l'AUTRE écriture est le même sur le devis et sur la fiche, et si elle n'est pas liée (S-51) | intégration, les deux branches : nom identique ⇒ fiche complétée ; nom différent ⇒ fiche intacte, copie complétée |
| **MD-9** | **Le découpage du nom mal tombé à la conversion** — prénom composé (« Abd El Kader », « عبد القادر ») ou nom écrit avant le prénom ; sans espace, un prénom inventé | module pur de l'écran (`decouperNom` : avant le PREMIER espace ⇒ prénom, le reste ⇒ nom ; sans espace ⇒ tout au nom, prénom vide) ; les deux champs restent MODIFIABLES ; rien n'est stocké | unitaire (les cas de la consigne) ; composant : corriger les deux champs à la main, puis l'envoi de `convert` porte la valeur de l'ÉCRAN ; prénom vide ⇒ conclusion bloquée |
| **MD-10** | **Un pro apprend qu'un compte existe** (M-4) : corps, statut ou forme différents entre un identifiant connu d'un compte Zwadj et un inconnu | K-1 ne lit JAMAIS `users` (garde de source : le chemin de la recherche ne nomme ni le modèle ni la table) ; il ne cherche que dans les fiches du pro | intégration : **égalité stricte** (statut ET corps) entre un numéro porté par un compte et un numéro inconnu, et de même pour l'e-mail ; la garde de source |
| **MD-11** | **La fiche d'un AUTRE pro** visible ou utilisable | toute lecture et écriture passe par `pro_profile_id` du pro connecté (la propriété se traverse par la relation, D149) | intégration : K-1 ne la trouve pas ; K-3, K-3b et K-4 avec son identifiant ⇒ `404` indistinct |
| **MD-12** | **Le PDF imprime une valeur non stockée** (M-7) : le compte (`quotes.client_id → users`), la fiche vivante, l'autre écriture | la source du document ne lit que la COPIE du devis, celle de la langue du document (S-52) ; absente ⇒ « — » | intégration : la copie est imprimée ; la fiche modifiée après la création ne change pas le PDF ; copie absente dans la langue ⇒ « — » |
| **MD-13** | **La migration échoue sur une base non vide** (D123), ou réécrit des devis existants | colonnes neuves NULLABLES ; table neuve vide ; aucune reprise de données | `migration-non-empty.int-spec.ts` re-pointé sur la migration neuve : des devis existants la traversent, leurs colonnes neuves sont NULL |
| **MD-14** | **Un numéro non canonique en base** : l'unicité `(pro, numéro)` devient muette (M-2) | le `CHECK` de forme sur la colonne neuve (S-50 : `phone ~ '^\+213[567][0-9]{8}$'`) | intégration : une écriture non canonique est refusée par la base ; l'expression du `CHECK` est confrontée à `DZ_MOBILE_E164` |
| **MD-15** | **K-4 mal borné** : un nom sans fiche ; une fiche sans nom ; `clientId` encore accepté (DB-15) | le contrat (`quoteCreateSchema`, strict) | unitaire et intégration : noms sans fiche ⇒ `400` ; fiche sans nom ⇒ `400` ; `clientId` ⇒ `400` (clé inconnue) ; sans fiche ⇒ le devis se crée comme aujourd'hui |
| **MD-16** | **Une révision recopie la fiche vivante** au lieu du nom du devis précédent (R8 amendée, D329) | la révision porte le corps entier (la copie fournie par l'écran, préremplie du devis précédent) ; le serveur n'y substitue rien | intégration : fiche modifiée entre deux versions ⇒ la révision porte la copie fournie, pas la fiche |
| **MD-17** | **L'écran du pro** : le contact n'est pas la première étape ; une recherche qui montre une donnée du compte ; une fiche trouvée dont les noms écraseraient la fiche ; la conversion qui réécrit la fiche | l'écran : contact d'abord (numéro puis e-mail), puis les noms ; une fiche trouvée PRÉREMPLIT les noms de CE devis ; la conversion n'appelle aucune route des fiches | composant : l'ordre des étapes ; les appels et leurs corps ; aucune écriture de fiche après la création ; la fiche liée grisée |

⚠ **Ce que ces gardes ne couvrent pas** (écrit, pas couvert) : le mélange de chiffres arabo-indiens et latins (HORS LOT) ; la demande ou la visite en cours (exception R4, L35-5) ; la fusion (L35-6) — `linked_user_id` n'est écrit par AUCUN code de ce lot, la fiche liée n'existe qu'en test ; la traduction des noms (L36-6) ; la réservation par e-mail seul (L36-1) ; un contrôle d'écriture par champ (un nom latin tapé dans le champ arabe : M-22, non décidé) ; l'idempotence d'un double clic sur la CRÉATION d'un devis (M-17, inchangé).
