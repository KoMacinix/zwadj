# D348 — règle de la preuve e2e, commitée AVANT les passes (R-15 de D343)

1. **Les rouges avant le code** (D334, point 5) : `docs/preuves/D348/rouges/` est commité AVANT tout commit de code d'application. Chaque pièce porte l'empreinte sha256 du fichier joué. Si rien d'application n'est corrigé (R-5), les rouges sont ceux des gardes de la spec (cibles de `neutralisation/neutralize-pub1.py`) et précèdent le commit de la spec et du harnais.
2. **Chaque garde neuve mord** : chaque cible de `neutralisation/neutralize-pub1.py` est lue en `expect(...)` ; un délai d'action n'est pas une morsure, l'expiration d'une assertion web-first l'est (D323). Zéro muette, zéro non mesurée. **Un harnais modifié en cours de campagne ⇒ la campagne est rejouée EN ENTIER** (règle de campagne du rang 50 d'origine, reprise par la consigne, point 2 R-5/R-6).
3. **L'e2e complète DEUX fois de suite, sur secteur** (`pnpm test:e2e`, serveurs de développement). Attendu : le nombre de tests de la suite avant le lot (**88 passés + 1 ignoré**, D347) PLUS le nombre de tests de `r50-salle-publiee.e2e.ts` (relevé par `playwright test --list`, écrit au rapport avec la spec), chaque passe, zéro échec, aucun rejeu. Une passe rouge est **lue**, pas relancée ; un seul rejeu est permis s'il est décidé et écrit avant (par Ko ou le relecteur).
4. Poste : secteur (`BatteryStatus` = 2), RAM libre relevée, `chrome` et `headless_shell` à 0, Docker lancé, ports 3100/3101/5273/5274 libres, arbre propre. Batterie : aucune passe (R-9 de D340).
5. La première passe est celle du pilote `docs/preuves/D340/portes/passe-secteur.sh` (six portes en série, dont `test:e2e`) ; la seconde est `pnpm test:e2e` seul, juste après. Les deux sont rapportées avec leurs chiffres.
6. **M-3 (les délais, sur un build de production) ne fait PAS partie de la suite** : il se joue à part, sur `next build` et `next start`, avec la valeur RÉELLE du cache (aucune retouche de `revalidate`, donc rien à restaurer). Les serveurs de développement de l'e2e et le build n'utilisent pas `apps/client/.next` en même temps : les deux ne tournent jamais ensemble.
7. **Aucune écriture sur la base de développement de Ko.** L'e2e travaille sur `zwadj_e2e` (recréée à chaque lancement) ; M-3 travaille sur une base jetable créée pour la mesure, nommée et supprimée au rapport, sur le même serveur PostgreSQL de Docker. Toute écriture sur ce serveur est déclarée au rapport (commande, heure, effet).
8. **Les journaux bruts des serveurs portent des jetons de développement** (courriels d'activation journalisés) : ils sont versés MASQUÉS par `masquer-jetons.py` (copie de D345), avec « token= restants : 0 » assertés avant écriture ; ce qui ne peut pas être masqué n'est pas versé.
